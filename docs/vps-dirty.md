# VPS dirty и перенос Windows clean

В этой схеме Windows clean обращается к локальному CONNECT `127.0.0.1:18766`.
Matrix передает сигнализацию, WebRTC/TURN передает данные, а dirty на VPS
открывает соединения к разрешенным внешним сервисам. Прямое соединение clean
с VPS не требуется. VPN на VPS и рабочем компьютере настраивается отдельно.

## Замена потерянной dirty

В протоколе 3 адресат и открытый Ed25519-ключ закреплены в peer trust.
Новый вход в тот же Matrix-аккаунт не воспроизводит identity потерянной машины.
Нужна явная перепривязка clean; общий вход трех устройств в Matrix не создает
автоматический выбор dirty. Подробности обычного enrollment: [peer-trust.md](peer-trust.md).

Для переноса добавлен одноразовый enrollment через Matrix to-device:

- На dirty явно задаются `HF_PEER_TRUST_FILE` и `HF_PEER_ENROLLMENT_FILE`.
- Файл разрешения содержит случайный `token` и срок `expiresAt` в миллисекундах Unix.
- Приватный пакет clean содержит `enrollment.json`: `homeserver`, открытый
  дескриптор `dirty` (`userId`, `deviceId`, `publicKey`), тот же `token`, `expiresAt`.
- `node scripts/enroll-clean-vps.mjs <enrollment.json>` использует существующую
  Matrix-сессию clean или предлагает подтвердить новый вход. Оба устройства
  должны принадлежать одному аккаунту. Запрос и подтверждение связаны HMAC.
- Dirty сохраняет первый принятый clean-дескриптор, обновляет trust и
  перезапускается. Повтор для того же clean допускается; другое устройство
  не может использовать уже принятое разрешение. Приватный ключ clean остается
  на clean. Обычные сообщения продолжают проверяться по подписанному протоколу.

Начальный trust dirty должен быть валиден и соответствовать ее Matrix-сессии
и локальной identity; файл разрешения сам по себе этот trust не создает.
Файлы разрешений, Matrix-сессии и готовый персональный пакет нельзя публиковать
в GitHub. После истечения разрешения оператор выдает новое.

## Linux dirty

Dockerfile запускает `node scripts/run.mjs`; сторона выбирается через `HF_SIDE`.
Для dirty задаются `HF_SIDE=dirty`, `MATRIX_HOMESERVER_URL`, `HF_RUNTIME_ROOT=/data`,
`HF_PEER_TRUST_FILE=/data/peer-trust.json` и при переносе
`HF_PEER_ENROLLMENT_FILE=/data/secrets/enrollment.json`.
Каталог `/data` должен храниться в постоянном томе. В нем остаются Matrix-сессия,
обновляемый refresh token, identity и trust. Повторная авторизация не нужна
после обычного перезапуска контейнера.

На Windows приватные ключи и refresh token используют DPAPI текущего пользователя.
На Linux приватные файлы доступны только владельцу (файлы `0600`, каталоги `0700`);
историческое имя `release-private.dpapi` на Linux содержит PEM, а не DPAPI ciphertext.

Для VPS подходит отдельный контейнер с `--restart unless-stopped`, ограничениями
памяти/CPU и без опубликованных портов. Локальные RPC и панель нужны внутри
контейнера. Для этой схемы не требуется менять VPN, маршруты или правила firewall.

## Пакет для Windows clean

Подготовленный офлайн-пакет содержит `node.exe`, `package.json`, `package-lock.json`,
`src`, `scripts`, `dist`, production `node_modules` и персональный `enrollment.json`.
Стартовый CMD вызывает `scripts/setup-clean-vps.ps1`; скрипт также доступен через
`scripts/install-clean-vps.cmd`. Сам репозиторий не содержит Node и персонального разрешения.

1. Распаковать пакет целиком и запустить CMD под обычным Windows-пользователем,
   у которого работала прежняя Matrix-труба.
2. При запросе подтвердить Matrix-вход. Дождаться `READY` и зеленого значка.
3. Открыть привычный VS Code с прежним локальным proxy и проверить запрос Codex.

Установщик сохраняет XML прежней задачи `HFPipe-clean`, копирует runtime в
`%USERPROFILE%\.hf-pipe\vps-clean\app`, привязывает identity и проверяет реальный
datachannel. После успеха регистрирует `HFPipe-clean-vps` при входе пользователя
и отключает прежнюю задачу. При ошибке восстанавливает ее прежнее состояние.
Режим `-TestOnly` проверяет установку без регистрации новой задачи.

Панель: `http://127.0.0.1:18764/`. Логи: `%USERPROFILE%\.hf-pipe\vps-clean`.
Контроль процесса перезапускает зависший worker; окно восстановления RTC —
120 секунд, чтобы внешний таймер не прерывал штатную попытку соединения.
Автовосстановление не гарантирует отсутствие обрывов и не заменяет проверку
в конкретной рабочей сети.

## WebRTC handshake

Зависимость `werift` закреплена на `0.24.4`. `npm ci` запускает
`scripts/patch-werift.mjs`: он проверяет версию и ожидаемые участки исходников,
затем применяет одинаковую поправку к ESM и CJS. Если установка использует
`--ignore-scripts`, этот скрипт нужно выполнить явно; Dockerfile делает это
до сборки. Подготовленный офлайн-пакет уже содержит исправленные зависимости.

Поправка запрещает позднему повтору DTLS ServerHelloDone сбрасывать завершенный
handshake и сериализует запуск ICE/DTLS/SCTP. Готовый ICE больше не пропускает
оставшиеся стадии. Проверка fingerprint, шифрование и обработка настоящих
ошибок сохраняются. Сигналинг передает один готовый SDP; прием старых trickle
кандидатов сохраняется.

`tests/rtc-handshake-recovery.test.mjs` проверяет публичный datachannel через
локальный UDP proxy: после открытия повторяет реальный ServerHelloDone,
ждет прежнее 33-секундное окно отказа и снова передает уникальное сообщение.
Внешние STUN/TURN для этой проверки не используются.
